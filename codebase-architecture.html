Ground-up codebase walkthrough

How the Vigil backend turns missed calls into recoverable plumbing leads.

This page explains the codebase as it exists in this repository: a Python/FastAPI backend that receives Twilio webhooks, stores operational records in Supabase, runs a deterministic plumbing SMS decision tree, sends approved SMS templates, and records enough audit trail to understand every automated decision.

Application FastAPI webhook backend
Integrations Twilio + Supabase
Workflow Brain Deterministic decision tree
Primary Product Path Missed call -> SMS recovery -> owner handoff

Overview

Vigil is a managed missed-call recovery service for plumbing shops. The codebase implements the backend piece of that service. Contractors conditionally forward unanswered calls to a Vigil-controlled Twilio number. Twilio notifies this backend. The backend identifies which contractor owns the Twilio number, records the event, sends a recovery SMS, processes the customer's SMS or MMS reply, asks for missing facts, and eventually alerts the owner with a structured lead summary.

Customer Calls the contractor, then replies by SMS or MMS.
Twilio Receives forwarded voice calls and inbound SMS payloads.
FastAPI Validates, deduplicates, parses, and delegates webhooks.
Workflow Services Coordinate leads, conversations, decision runs, and side effects.
Supabase Persists clients, leads, messages, calls, opt-outs, media, and audits.
The most important design choice: the decision tree does not send texts or write data itself. It returns typed actions. The action executor turns those actions into Twilio sends and Supabase writes. That keeps routing logic auditable and prevents arbitrary generated prose or arbitrary code execution.

Runtime Code

backend/app/main.py owns app creation, environment loading, webhook routes, TwiML responses, Twilio signature validation, idempotency wrappers, and global clients.

Business Logic

backend/app/services owns workflow orchestration and side effects. This layer is where "what happens when a missed call or SMS arrives?" is answered.

Pure Routing Logic

backend/app/decision_tree owns classification, decision selection, action contracts, and approved SMS template rendering.

Mental Model

Read the system as five layers. Each layer has a narrow job and hands structured data to the next layer.

1. Network Boundary
Twilio voice webhook Twilio SMS webhook Twilio status callback
2. HTTP Boundary
FastAPI routes form parsing signature validation TwiML responses
3. Workflow Layer
missed_call_recovery sms_workflow action_executor
4. Domain Brain
classifier interpreter templates typed contracts
5. Persistence
clients leads conversations messages call_events decision_tree_runs owner_notifications webhook_events

The data flow is intentionally unidirectional during request handling: route -> service -> repositories and decision tree -> action executor -> repositories/Twilio. Repository modules do not call services. The decision tree does not call repositories. The route layer does not contain the detailed lead-recovery algorithm.

Boot And Configuration

backend/app/main.py is loaded when the ASGI server imports app.main:app. At import time it reads environment configuration, creates integration clients if credentials are present, and configures security behavior.

Environment Sources

The helper env_value() checks real process environment first, then falls back to backend/.env loaded through python-dotenv.

SUPABASE_URL SUPABASE_SERVICE_ROLE_KEY TWILIO_ACCOUNT_SID TWILIO_AUTH_TOKEN PUBLIC_BASE_URL TWILIO_STATUS_CALLBACK_URL APP_ENV TWILIO_VALIDATE_SIGNATURE

Global Runtime Objects

If Supabase credentials exist, create_client() creates supabase. If Twilio credentials exist, TwilioClient() creates twilio_client. If the Twilio auth token exists, RequestValidator creates twilio_validator.

Missing credentials do not crash import. They print configuration warnings and routes later skip work or raise where a send is required.

Signature validation switch: TWILIO_VALIDATE_SIGNATURE=false only disables validation in local/development/test-like environments. In production-like environments, the code ignores that disable flag and keeps validation enabled.

Webhook Layer

The backend exposes four HTTP routes. One is health-only; three are Twilio entry points.

Route Caller Main Job Response
GET /health Uptime checks Returns a simple readiness marker. {"status":"ok"}
POST /webhooks/twilio/voice Twilio voice Handle forwarded missed calls and trigger initial recovery SMS. Answer-and-hangup TwiML
POST /webhooks/twilio/sms Twilio messaging Handle customer replies, run the decision tree, and execute actions. Empty TwiML
POST /webhooks/twilio/status Twilio messaging status Update message delivery status by Twilio SID. Empty TwiML

Shared Route Mechanics

Parse form data.

Twilio sends form-encoded payloads. form_to_dict() converts FastAPI's form object into a plain dict[str, str]. form_value() pulls known fields safely.

Validate the Twilio signature.

twilio_signature_is_valid() reconstructs the public URL and asks Twilio's RequestValidator to validate X-Twilio-Signature. public_request_url() respects PUBLIC_BASE_URL, forwarded headers, and request URL details.

Begin an idempotency event.

begin_twilio_webhook_event() stores or checks webhook_events when Supabase and that repository are available. If persistent idempotency fails, it falls back to a process-local set.

Delegate to workflow code.

The route calls process_missed_call(), process_inbound_sms(), or update_message_status_by_twilio_sid().

Mark processed and return TwiML.

mark_twilio_webhook_event_processed() records completion when possible. Routes return XML TwiML even when the backend skips work, because Twilio needs a clean response.

Voice Flow

A voice webhook represents the missed-call recovery trigger. The route itself stays thin after parsing, validation, and idempotency. The service process_missed_call() owns the behavior.

Twilio sends From, To, CallSid, and CallStatus.

From is the caller/customer. To is the Vigil Twilio auxiliary number. CallSid is used as the provider event ID.

The route suppresses duplicate webhook deliveries.

The event type is voice:{CallStatus}. A duplicate returns the same answer-and-hangup TwiML without re-running recovery side effects.

The service identifies the client by the Twilio number.

clients_repo.find_client_for_voice_number() first checks client_phone_numbers with voice_enabled=true and active=true. It can fall back to legacy clients.twilio_phone.

If the number is unknown, the call is logged but no customer SMS is sent.

The service inserts a call_events row with nullable client and lead IDs, then returns processed=false with unknown_twilio_number.

Known clients get a lead and active SMS conversation.

leads_repo.upsert_lead() upserts by (client_id, phone_number). conversations_repo.get_or_create_active_conversation() ensures there is one non-closed SMS conversation.

The call event is stored before suppression decisions.

This preserves observability even if the caller is opted out or recently texted.

Opt-out and duplicate suppression prevent unwanted text.

opt_outs_repo.is_opted_out() blocks opted-out numbers. messages_repo.recent_recovery_sms_exists() blocks repeated missed_call_initial sends within 60 minutes.

The initial recovery SMS is rendered and sent.

render_template("missed_call_initial") includes the business name. The SMS is sent from the webhook To number to the caller's From number.

The outbound message and conversation state are persisted.

The service inserts an outbound messages row and updates the conversation to waiting_for_customer / awaiting_initial_reply.

Why the voice route answers and hangs up: the TwiML says a short line and then hangs up. The comment in main.py explains that answering the forwarded leg lets the carrier stop ringing the original client phone, whereas rejecting the call can be treated as forwarding failure.

SMS Flow

SMS is the richer workflow. Every inbound customer reply is logged, classified, audited, transformed into explicit actions, and used to update persistent conversation state.

Twilio sends customer reply fields.

The route reads From, To, Body, MessageSid, and MMS fields like NumMedia, MediaUrl0, and MediaContentType0.

Media metadata is parsed before service delegation.

parse_inbound_media() accepts NumMedia but also scans actual MediaUrlN keys, so it is resilient to payloads with inconsistent media count fields.

Inbound SMS idempotency uses MessageSid.

The event type is sms:inbound. Duplicate webhooks return empty TwiML and do not insert duplicate messages or send duplicate replies.

The service validates basic requirements.

process_inbound_sms() skips if from_phone or to_phone is missing, or if Supabase is not configured.

The client is resolved through SMS-enabled phone mapping.

clients_repo.find_client_for_sms_number() checks client_phone_numbers with sms_enabled=true and active status, with a legacy fallback.

The lead and conversation are loaded or created.

The lead status is set to sms_reply. The conversation supplies the current state and previously collected facts.

The inbound message and media records are inserted.

The inbound messages row stores direction, phones, body, Twilio SID, status received, raw payload, and conversation ID. Each attachment gets a message_media row.

Conversation facts are prepared.

collected_info starts from the persisted conversation. If any media is present, photo_received=true is added before the decision tree runs.

The plumbing decision tree runs.

run_plumbing_decision_tree() takes the message body, current conversation state, and collected facts. It returns DecisionResult with a matched node, actions, next state, status, facts, and summary.

The decision is audited.

decision_tree_runs_repo.insert_decision_tree_run() stores the tree key/version, classifier output, matched node key, action JSON, result status, and inbound message ID.

Actions are executed in order.

execute_actions() renders approved templates, sends SMS, updates leads, creates opt-outs, notifies owners, and closes conversations as directed by the typed actions.

The conversation is updated with the decision result.

The final update writes status, current_state, collected_info, summary, last_message_at, and closed_at when the result is closed.

Status Callback Flow

Outbound Twilio sends can include a status callback URL. The route POST /webhooks/twilio/status receives delivery updates and keeps messages.status current.

Callback URL Resolution

twilio_status_callback_url() prefers TWILIO_STATUS_CALLBACK_URL. If not set, it builds {PUBLIC_BASE_URL}/webhooks/twilio/status. If neither exists, sends omit the callback.

Status Update

The status route reads MessageSid and either MessageStatus or SmsStatus, deduplicates by sms:status:{status}, and calls messages_repo.update_message_status().

Decision Tree

The decision tree package is the deterministic workflow brain. It turns a customer message into structured classification, then into safe actions. It never talks to Twilio or Supabase.

Contract Objects

contract.py defines the vocabulary shared between the tree and executor.

  • ClassifierOutput: intent, confidence, summary, urgency, job type, location, lead signal, reason.
  • DecisionAction: action type plus action-specific fields like template key, lead status, opt-out reason, or notification priority.
  • DecisionResult: tree identity, classifier output, matched node, actions, next conversation state/status, collected facts, and summary.

Base Tree Vocabulary

trees/base/plumbing_default.py stores the current tree key plumbing_missed_call_recovery, version 2026-06-05, required facts, opt-out phrases, wrong-number phrases, job keywords, urgency keywords, and GTA location hints.

Classifier

classify_plumbing_sms() is regex and keyword based. It normalizes text, checks special intents first, extracts location/job/urgency facts, and returns unclear only when no route can be matched.

Detection How It Works Output Effect
Opt-out Exact words like STOP or phrases like "do not text". intent="opt_out", high confidence, no lead signal.
Wrong number Phrases like "wrong number" or "you have the wrong". intent="wrong_number".
No longer needed Exact or phrase matches like "already fixed" and "no longer need". intent="no_longer_needed".
Location Street address regex, Canadian postal code regex, "near/around/at" pattern, GTA city names, or free text while awaiting location. Fills location.
Job type Keyword groups for leak/pipe, drain/sewer, water heater, fixture/install, and quote/estimate. Fills job_type.
Urgency Keyword groups for quote, scheduled, emergency, and today. The current priority order is quote -> scheduled -> emergency -> today. Fills urgency.

Interpreter

run_plumbing_decision_tree() merges any newly extracted facts into collected_info, preserves emergency urgency from being downgraded by later replies, creates a summary, and chooses a matched node.

awaiting_initial_reply Default state after missed-call SMS.
awaiting_location Customer has signaled interest but no location is known.
awaiting_job_type Location is known, but service category is missing.
awaiting_urgency Location and job type are known, but timing is missing.
closed Opt-out, lost, wrong number, or handoff complete.
Matched Node Condition Actions Next State
opt_out Classifier intent is opt-out. Confirm, create opt-out, mark lead opted out, close. closed
wrong_number Classifier intent is wrong number. Confirm, create wrong-number opt-out, mark lead, close. closed
no_longer_needed Customer says they are all set. Send close-out text, mark lead lost, close. closed
fallback_unclear Initial reply is unclear. Ask for clarification, mark lead needs clarification. awaiting_initial_reply
emergency_collect_location Emergency detected but location missing and owner not already notified. Notify owner urgent, acknowledge emergency, mark emergency. awaiting_location
collect_location Location is missing. Request location, mark lead needs location or emergency. awaiting_location
collect_job_type Location exists but job type is missing. Request job type, mark lead needs job type or emergency. awaiting_job_type
collect_urgency Location and job type exist but urgency is missing. Request urgency, mark lead needs urgency. awaiting_urgency
lead_complete_handoff Required facts are known. Confirm handoff, notify owner unless already handled, mark lead, close. closed

Template Renderer

templates/base.py stores approved copy in DEFAULT_TEMPLATES. render_template() formats copy with business name, lead phone, collected facts, photo status, priority, latest message, and summary. Missing values become readable fallbacks like Unknown rather than leaking braces to the customer.

Action Executor

services/action_executor.py is the bridge between pure decisions and external side effects. It loops through DecisionResult.actions in order and dispatches by action type.

Action Type Executor Function Side Effects Failure Behavior
send_sms_template _execute_send_sms_template() Renders approved template, checks opt-out, sends customer SMS, inserts outbound message. Twilio send exceptions are caught; message row is inserted with failed. Opt-outs create suppressed_opt_out message rows.
mark_lead_status _execute_mark_lead_status() Updates leads.status, updated_at, and optional summary. Missing lead_status raises ValueError.
create_opt_out _execute_create_opt_out() Creates idempotent opt-out row with reason and source. Repository retries by reading existing row on insert conflict.
notify_owner _execute_notify_owner() Renders owner summary, sends SMS to clients.owner_phone, inserts owner notification row. Missing owner phone, owner phone matching customer, or Twilio failure creates a failed notification row.
close_conversation _execute_close_conversation() Calls repository close helper, setting status/state/closed time and preserving final info. Repository errors propagate.
Important subtlety: the SMS workflow also performs a final update_conversation() after actions execute. That means a close_conversation action closes immediately, and the final update then writes the same final status/state/summary from the DecisionResult.

Supabase Schema

The migrations in this repo add mapping, media, idempotency, and workflow-safety constraints around an existing operational schema. The application expects the base tables clients, leads, conversations, messages, call_events, opt_outs, decision_tree_runs, and owner_notifications to exist.

New Tables In Migrations

  • client_phone_numbers: maps active Twilio numbers to clients and flags whether each number supports voice and SMS.
  • webhook_events: stores provider/event IDs and request hashes for idempotent webhook processing.
  • message_media: stores Twilio media URLs and content types tied to inbound messages.

Important Constraints And Indexes

  • leads(client_id, phone_number) unique because lead upsert depends on it.
  • messages(twilio_message_sid) unique when not null.
  • One active conversation per (client_id, lead_id, channel).
  • opt_outs(client_id, phone_number) unique.
  • webhook_events unique on provider/event/provider event ID or provider/event/request hash.

Entity Relationships

Entity Relationship Why It Exists
clients One client has many phone-number mappings, leads, conversations, messages, call events, opt-outs, notifications, and decision runs. Represents a contractor account.
client_phone_numbers Many numbers belong to one client. Allows one contractor to have multiple Vigil-controlled numbers or different voice/SMS enablement.
leads One lead belongs to one client and can have conversations/messages/calls. Represents the customer phone number for that contractor.
conversations One active SMS conversation per client/lead/channel. Stores persistent state and collected facts between replies.
messages Each message belongs to client/lead and usually a conversation. Audits every inbound/outbound SMS and delivery status.
message_media Many media rows can belong to one message. Preserves MMS/photo context and owner notification photo status.
decision_tree_runs Each run ties to an inbound message, client, lead, and conversation. Makes automated decisions debuggable and trustable.
owner_notifications Each row ties notification outcome to client, lead, and conversation. Tracks handoffs and notification failures.
webhook_events Independent idempotency ledger keyed by provider, event type, ID/hash. Prevents Twilio retries from duplicating side effects.

Cross-Cutting Concerns

Idempotency

Twilio retries are expected. webhook_events is the persistent guard. Voice events use CallSid plus event type/status. Inbound SMS uses MessageSid. Status callbacks use MessageSid plus status. If Supabase idempotency is unavailable, the process-local set prevents duplicates only within the current process lifetime.

Security

Twilio request signatures are validated when enabled. Validation is designed to stay enabled outside local/test environments. Supabase service-role access is server-side only. The code logs operational values like phones and message lengths, so production logging should be reviewed for PII minimization before broader deployment.

Opt-Out Safety

Missed-call recovery checks opt-outs before first customer SMS. Decision-tree reply SMS also checks opt-outs before sending. STOP and wrong-number inbound messages still process so an opt-out can be recorded.

Auditing

Messages store the actual SMS records, decision_tree_runs stores why the automation chose its route, owner_notifications stores handoff attempts, and webhook_events stores delivery-level processing history.

Conversation State

Conversation state is what lets the tree ask only for missing facts. State and collected_info are loaded before classification and persisted after action execution.

Approved Copy

Customer-facing SMS is selected by template key, not generated freely. This protects the service from arbitrary AI copy and keeps client-approved language inspectable in source.

Current Edges

The codebase implements a strong MVP backend path, but a few technical edges are worth knowing when operating or extending it.

Area Current State Why It Matters
Base schema The repo includes additive migrations but not the original creation migrations for every expected table. A fresh database needs base tables created elsewhere before these migrations are enough.
Client-specific templates/trees Templates and tree vocabulary are source-defined defaults. Good for MVP auditability, but future client-specific behavior needs versioned storage and approval workflow.
Durable media storage MMS metadata is stored; Twilio media is not copied into Supabase Storage. Twilio media URLs may not be a permanent archive, so long-term photo access may require copying.
Phone normalization Lookups compare phone strings as supplied. Production reliability improves if all phone numbers are normalized to E.164 at boundaries.
Error handling Routes catch broad exceptions and print errors, returning TwiML. Operational visibility should eventually move to structured logs and human-facing failure alerts.
Process-local fallback idempotency If persistent idempotency fails, duplicates are suppressed only in the current process memory. Multi-process or restarted deployments need the webhook_events table functioning.

Glossary

Lead

A customer phone number in relation to one contractor client. The same phone number could be a separate lead for a different client.

Conversation

The active SMS workflow state for a lead. It stores what the automation already knows and what it is waiting for next.

Decision Run

An audit record of one inbound SMS going through classifier and interpreter, including matched node and planned actions.

Action

A typed instruction from the decision tree, such as sending an approved template, marking a lead status, or notifying the owner.

TwiML

XML returned to Twilio that tells it what to do with a call or message webhook. This code returns either answer-and-hangup voice TwiML or empty response TwiML.

Webhook Event

A persistence record used to determine whether a Twilio webhook delivery is new or a retry that should not run side effects again.
